# Runtime Modes

Validated: 2026-07-15
Purpose: describe the app's actual runtime modes and the current integration seams between the Expo app and the API package.

## Canonical Sources

- `constants/config.ts`
- `services/api-client.ts`
- `services/auth-service.ts`
- `packages/config/src/env.ts`
- `apps/api/src/app.ts`

## V1 Runtime Rule: DB/API First

Clubroom V1 product behavior must be backed by Fastify `/v1` contracts and the `db` backend. Local mock/demo storage is not product authority.

Allowed exceptions:

- `NODE_ENV=test` harnesses that exercise retained compatibility branches
- A local debug native audit with all of `EXPO_PUBLIC_NATIVE_AUDIT_TEST_MODE=true`, `EXPO_PUBLIC_USE_MOCK=true`, `EXPO_PUBLIC_REVYL_AUTH_BYPASS_ENABLED=true`, and a non-empty local bypass token. This is development-environment-only (`EXPO_PUBLIC_ENV=development`); it uses existing demo fixtures, never calls Fastify or Supabase. Protected child-management and parent-only child-progress routes default-deny unless the signed-in mock actor declares that child relationship. Development player-detail and support routes default-deny unless the actor is that player, a declared parent, or an assigned coach; coach emergency and roster session-adder routes require an assigned roster entry. Staging and production fail closed. It is owned by the native-audit work and must be removed once staging has an approved disposable role-session harness.
- deterministic seed/import tooling used to populate a real database
- unavoidable temporary provider gaps, where the backend owns the simulated boundary and the UI does not claim real-world completion

Destructive seed/import tooling must require explicit local/staging confirmation before connecting to Prisma or clearing product tables.

When a feature has no `/v1` contract yet, add the DB-backed contract, fail closed, return an honest empty/no-op state, or document a named cutover task. Do not add new local mock/demo data as a V1 product path.

## Retained Test Fixture Path: Mock Local-First

Flags:

- `EXPO_PUBLIC_USE_MOCK=true`

Behavior:

- Only allowed when `NODE_ENV=test`.
- The one temporary exception is a local debug native audit with `EXPO_PUBLIC_NATIVE_AUDIT_TEST_MODE=true`; it additionally requires the app's role-entry bypass to be enabled and token-verified. Expo Router's `/revyl-auth` route is the single allowlisted evaluator, so an intercepted link either replaces the exact local demo role or renders a visible rejection. It is not permitted in staging or production configuration.
- Feature services can still exercise retained mock branches through `apiClient`.
- `apiClient` persists to AsyncStorage-backed storage in test harnesses.
- Normal Expo app runtimes reject this flag at startup and must use `/v1`.
- Mock local-first behavior is never live V1 product truth.

Use when:

- running retained service tests while `/v1` cutover finishes
- proving a legacy branch has been safely replaced or made unreachable

## Retired Mode: Pre-API Live

Rejected flag:

- `EXPO_PUBLIC_USE_MOCK=true`
- `EXPO_PUBLIC_PRE_API_LIVE_MODE=true`

Behavior:

- No longer supported in app runtime config.
- The app shell no longer imports or starts any pre-API live bootstrap service.
- Auth login, signup, onboarding, session restore, and Coach Development screen loads no longer invoke coach-session demo seeding in API mode; authenticated product state must be loaded by the feature-owned `/v1` service path. Coach Development reads awaiting-completion work through booking authority and recent/attention session history through `/v1/coaches/:coachId/development-sessions`, backed by `SessionFeedback` truth.
- Home and My Progress do not invoke progress demo seeders before live reads; retained seed entrypoints are compatibility-only and must not be product runtime bootstraps.
- `services/relational-demo-seed-service.ts` preserves the `ensureRelationalDemoSeeded()` caller contract but no longer creates or repairs local demo users, bookings, offerings, invites, family, club, safety, messaging, review, or coach-directory records.
- Live product behavior should come from real `/v1` services instead.

Use when:

- never; use real API mode for live product behavior

## Normal Runtime: Real API

Flags:

- `EXPO_PUBLIC_USE_MOCK=false`
- `EXPO_PUBLIC_PRE_API_LIVE_MODE=false`

Target behavior:

- Frontend still goes through `apiClient`
- Reads and writes should hit the Fastify API instead of local persistence
- Server-owned product data should persist through the `db` backend.
- This is the default runtime direction for app/API development and the V1 rule for product work.

## Staging Readiness Tooling

Use `node ./scripts/db-staging-preflight.js` before switching a serious rehearsal to `API_DATA_BACKEND=db`.
The preflight loads `.env.staging.local` by default when present, without overriding already-exported shell variables.

The preflight checks:

- staging env requirements for database, JWT, password reset email delivery, dev-outbox disabled state, simulated payment return origins, simulated payment secret, object storage, and Sentry warnings
- checked-in Prisma schema and migration presence
- local tool availability for API tests, root typecheck, Prettier, and Expo

Use `node ./scripts/db-staging-preflight.js --strict` as the hard gate once the staging environment values are expected to exist.
Use `node ./scripts/db-staging-preflight.js --write` to write transient outputs under `reviews/`.

For API-mode staging startup, start Fastify with the same staging env the app and smoke runner use: `npm --prefix apps/api run dev:staging` or `npm run api:dev:staging`.
The canonical staging command is intentionally non-watch so readiness smoke does not depend on local file-watcher limits.
Use `npm --prefix apps/api run dev:staging:watch` only when active API editing needs reload behavior and the local OS watcher limit can support it.
Use `npm run smoke:api-mode` before starting Expo in API mode. It loads `.env.staging.local`, confirms `EXPO_PUBLIC_USE_MOCK=false`, and verifies the configured Fastify API responds at `/v1/ready`.
If the configured API URL is a LAN address, the API must bind to `API_HOST=0.0.0.0`; otherwise loopback can respond while the app-configured origin still fails.
Use `npm run smoke:api-mode:strict` before release-ready staging rehearsal; strict mode requires `/v1/ready` to report `ready`, not merely reachable.

Use `npm run smoke:staging` after migrations and seed import are applied to prove the db-backed API path against the configured staging Supabase project. The command fails closed unless `EXPO_PUBLIC_ENV` or `SENTRY_ENVIRONMENT` resolves to `staging`, rejects production environment hints and production-looking database URLs, and requires `DATABASE_URL`; `NODE_ENV=production` remains valid because staging exercises production runtime behavior.
The smoke run loads `.env.staging.local` when present and verifies bearer auth, identity, coach profile/offerings, bookable slots, session invite create/cancel/accept booking creation, direct booking creation, invoice generation, simulated payment confirmation, simulated payout completion/removal, direct-payment instruction DB/audit redaction, coach delivery completion with attendance/session-note proof readback, allowed family/athlete sensitive reads, family health write/readback with DB/audit proof, denied unrelated-athlete sensitive reads, report auto-block/block soft-removal audit readback, safeguarding denied-read/action audit readback, club create/invite-code/join/archive audit readback, match invites, club schedule match projection, event RSVP/attendance DB readback, group-session creation/registration with booking/invoice/thread DB/audit proof, group-session chat message/read receipt DB/audit proof, private signed upload/readback, and community/media read surfaces.
Before and after those checks, it retires only records carrying the runner's exact staging markers, including linked bookings and simulated payout rows. The family-health check snapshots medical, emergency-contact, and consent state through the authenticated API and restores it through the same audited routes in `finally`; audit history is retained.
It treats release-only delivery/observability config (`PASSWORD_RESET_EMAIL_DELIVERY_MISSING`, legacy `PASSWORD_RESET_EMAIL_WEBHOOK_MISSING`, `PASSWORD_RESET_DEV_OUTBOX_ENABLED`, `SENTRY_DSN_MISSING`, and `SENTRY_RELEASE_DEFAULT`) as smoke warnings because strict staging preflight owns those release blockers, but fails on database, object-storage, auth, booking, payment, family, or media route drift.

Use `npm run launch:readiness` for the launch automation runner. It writes timestamped and latest reports under `reviews/`, runs `audit:worktree:strict`, `verify:slice:full`, `audit:agentic`, `audit:db:stage:strict`, `smoke:password-reset-webhook`, `smoke:api-mode:strict`, `smoke:staging`, and `ui:flows:run`, starts local staging API/UI servers when needed, rejects stale local API servers with launch-incompatible rate limits, paces the browser flow gate, and records live payment-provider cutover as deferred while keeping simulated/manual money-state safety in scope. The strict DB staging preflight connects to the configured Supabase/Postgres database and checks applied Prisma migrations plus schema columns required by current `/v1` db-mode routes.

## Safe Working Rules

1. Do not bypass `apiClient` in feature code.
2. When touching auth or API URL config, update both the app-side config and the API package assumptions together.
3. When switching a flow from mock to real API, keep the service contract stable and move the source of truth behind the service boundary.
4. Use `EXPO_PUBLIC_USE_MOCK=true` only in `NODE_ENV=test` harnesses or the explicit local native-audit exception above; normal app runtimes must use `/v1`.
5. Staging and production frontend config must boot in API mode. Development mock and pre-API live flags are app-runtime blocking errors unless the local native-audit exception is fully enabled.
6. New V1 product work should create or extend the DB-backed `/v1` authority instead of adding mock/demo fixtures. If a temporary exception is unavoidable, name the owner, cutover target, and removal condition in the smallest canonical doc or task packet.
7. `npm run audit:api-boundaries` rejects direct API-mode branches that skip live work and return `ok(undefined)`; call `/v1` or return an explicit service error instead.
8. Frontend runtime code must not import `@supabase/supabase-js` or call Supabase REST/GraphQL Data API paths; `npm run audit:api-boundaries` enforces Fastify `/v1` as the product-data boundary.
